> 好问题,而且方向完全对——你想做的其实就是"用 旧代码助手 的子 agent 把这个 skill 重写成一个迷你 STORM"。我先确认一下 旧代码助手 现在子 agent 的具体能力和多 agent 的成本情况,免得给你过时的建议。
>
> 能,而且这几乎是教科书级的应用场景。你想补的"多对抗性检索",正好是 旧代码助手 子 agent / Workflow 这套东西生来要解决的问题。先把概念理清:**"多 agent 管理"是 旧代码助手 这个壳(harness)的能力,不是模型权重里的东西**——Opus 4.8 是个很强的"指挥官"大脑,但调度的管子来自 旧代码助手 的 subagents / Agent Teams / Workflows。你完全可以让 Opus 4.8 当总控。
>
> **怎么映射到真 STORM**
>
> 真 STORM 的内核是:每个视角都跑一轮多轮对话,而且每个回答都落在检索到的真实来源上 → 汇成引用池 → 带引用地综合。多 agent 版本几乎一一对应:
>
> - **总控 agent**(Opus 4.8):拿到话题,定义 5 个视角,分派、收集、不亲自干粗活
> - **5 个视角子 agent 并行跑**:每个挂上 WebSearch/fetch,各自从自己的角度做检索循环,返回**带 URL 来源**的发现(不是凭记忆脑补)。怀疑论那个 agent 专门去找反证——这就是你说的"对抗性",而且比原版 STORM 还强,因为你是在**跨 agent 地主动找不一致**
> - **(可选第二轮)**:把各 agent 的简报互相喂给对方,让它们带着新检索互相反驳——真正的对抗动态
> - **矛盾地图**:在"有来源的主张"上找冲突,而不是在 vibes 上
> - **综合 agent**:从引用池里写带 citation 的简报
> - **独立的批判 agent**(全新上下文)做同行评审——这比原 skill 那种"自己给自己打分"靠谱得多
>
> **用哪个机制(这个有讲究)**
>
> 你这是个**固定流水线**(5 并行 → 矛盾 → 综合 → 评审),不是开放式"你看着办",所以:
>
> - 首选 **Workflows**(确定性编排)。旧助手 会现写一个编排脚本,并行 spin up 一队子 agent;它的 schema 选项能强制子 agent 调用结构化输出工具、在工具调用层校验、不匹配就重试——拿来强制每个视角 agent 必须吐"发现 + 来源 URL"的结构,正合适
> - 或者更简单:把 5 个视角写成 `.[已隐去service_branch]` 里的文件。子 agent 是可复用配置,YAML 里定义自己的系统提示、选用的模型、工具权限,在父会话里跑、回报结果,是最省 token 的一种
> - **Agent Teams** 只在你要让 agent 之间真的互相发消息(第二轮反驳)时才用。它最强也最贵,因为每一次 agent 间通信都是一次模型往返
>
> **诚实的几个坑(你会想知道的):**
>
> 一,**成本和延迟会炸**。5 个 agent 并行各做几轮搜+读,token 轻松是单轮对话的十几倍,还要等几分钟。对你这种要控成本的人,关键招:**worker 子 agent 用 Sonnet 4.6 或 Haiku 4.5,Opus 4.8 只留给总控+综合+批判**。子 agent 能逐个指定模型,一定要用上。
>
> 二,**真正的瓶颈是检索质量,不是编排**。这正好接上前两条我们聊的"死亡互联网"——你检索回来的东西本身有一大半是 AI 垃圾。如果子 agent 只是把 WebSearch 结果总结一下,你得到的是**排版精美、引用看着齐全的垃圾**。增量全在来源纪律上:每条发现强制带真实 URL、优先一手/学术源(Scholar、PubMed、arXiv、政府/行业报告)、让批判 agent **真的去核**每条主张能不能追到来源。你做哈普提克那篇的文献综述,最好是把 agent 接到真数据库(Semantic Scholar / arXiv 的 MCP),别只用通用搜索。
>
> 三,**自评分还是别全信**。独立 critic 在新上下文里评 > 自己评,但 LLM 给自己的置信分校准依然差,当启发式看。
>
> 四,**协调开销**。子 agent 各自独立上下文,总控负责拆解、分派、核验;但它们互相看不见,任务规格写不紧就会重复搜索或留缺口。schema 强制结构化输出能压住大半这个问题。
>
> 五,**别忘了机会成本**。storm.genie.stanford.edu 已经免费给你做带引用的综合了。自己搭多 agent 版值不值,取决于你要不要:① 自定义视角/prompt,② 把它集成进自己的 workflow / treepractice,③ STORM 没有的对抗辩论,④ 当作学练 harness 的项目(这条挺适合你)。要是只需要一份引用简报,直接用真 STORM 更省事。
>
> **对 skill 的改动本质上是:** 现在的 SKILL.md 是"单 agent 自己扮演五个角色";要变成真多 agent,Step 1 得改成"**spawn 5 个并行视角子 agent,每个带检索,每个必须返回带来源的发现**",而不是在一个上下文里自演。
>
> 要不要我直接给你写一版多 agent 的:要么是 `.[已隐去service_branch]` 里 5 个视角 agent + 一个总控 SKILL.md,要么是一个带 schema 强制来源的 Workflow 脚本?你说用哪种,我连"强制取证 + 独立 critic"一起给你搭好。
