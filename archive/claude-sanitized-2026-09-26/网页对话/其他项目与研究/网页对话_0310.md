> ## 支付宝当面付
>
> 这个是支付宝官方提供的一种支付能力，本来是给线下小商户用的（比如街边奶茶店扫码收钱），但个人开发者也能申请，因为它**不要求营业执照**。
>
> **工作原理很简单：** 你的网站后端调用支付宝 API，传入金额和订单号，支付宝返回一个付款链接，你把这个链接生成二维码展示在网页上，用户用支付宝扫码付款。付款成功后，支付宝会向你预设的回调地址发一个 POST 请求（Webhook），你的后端收到后验证签名、更新数据库里的订单状态，用户就变成已付费了。
>
> **申请流程：** 去支付宝开放平台（open.alipay.com）注册账号，选"自研开发者"，创建一个应用，在应用里申请"当面付"能力。审核时需要提交你网站的截图当作"门店照片"，一般 1-3 天通过。通过后你会拿到 AppID、商户私钥、支付宝公钥这三样东西，用它们就能调 API 了。
>
> **关键限制：** 单笔上限 1000 元，单日上限 5 万元。对订阅制来说绑绑有余。但它**没有自动扣款能力**——每个月到期了，用户得自己再扫一次码。另外它只能收支付宝的钱，微信用户付不了。
>
> **费率：** 0.6%，收 100 块钱支付宝抽 6 毛。钱直接结算到你绑定的支付宝账户对应的银行卡，T+1 到账。
>
> **技术集成：** 支付宝官方有 Node.js SDK（`alipay-sdk`），npm 装一下就能用。在你的 Next.js 项目里写个 API Route，大概长这样（伪代码逻辑）：
>
> 用户点"订阅" → 前端请求你的 `/api/pay` → 后端用 SDK 调支付宝的 `alipay.trade.precreate` 接口 → 拿到 `qr_code` 字段（一个 URL）→ 返回给前端 → 前端用 `qrcode` 库把 URL 渲染成二维码 → 用户扫码付款 → 支付宝 POST 到你的 `/api/pay/callback` → 验签 → 更新数据库
>

> ## XorPay
>
> XorPay 是一个第三方支付聚合平台，专门解决"个人开发者没有营业执照但想在网站上收微信/支付宝的钱"这个问题。
>
> **它为什么能做到这件事：** XorPay 是微信和支付宝的官方服务商，资金由微信/支付宝官方直接清算到你的个人银行卡，XorPay 自己不经手你的钱，只处理支付信息的中转。这是它合规性比较高的原因——它不是那种自己收了钱再转给你的"二清"模式。
>
> **工作原理和当面付几乎一样：** 你的后端调用 XorPay 的 API，传入金额、订单号、支付方式（微信或支付宝），XorPay 返回一个支付链接或二维码，用户扫码付款，成功后 XorPay 向你的回调地址发 Webhook。
>
> **申请流程：** 去 xorpay.com 注册，实名认证后充值 100 元作为预存款（这个钱会用于抵扣手续费，不是白交的），就能拿到 API 密钥开始用了。审核基本是即时的。
>
> **费率：** 大约 0.88%，比支付宝当面付的 0.6% 贵一点，但它同时支持微信和支付宝两个渠道，这是它的核心价值。
>
> **技术集成：** XorPay 的 API 非常简单，没有官方 SDK，但 API 就几个接口，直接用 `fetch` 调就行。下单接口 POST 一个请求过去，带上商户号、金额、回调地址和签名，返回支付二维码 URL。回调验签也很简单，就是 MD5 拼接验证。
>
> ---
>
> ## 两者怎么配合
>
> 最实用的组合是：**支付宝用当面付（官方渠道，费率低），微信用 XorPay（因为微信官方不对个人开放）**。
>
> 用户在你网站上点"订阅"时，弹出一个选择框让他选支付宝还是微信，然后走不同的后端逻辑生成对应的二维码。两个渠道的回调统一处理，更新同一张订阅表。
>
> 这个组合的好处是：支付宝那边走官方通道费率最低，微信那边虽然 XorPay 贵一点但至少能收到钱。总体综合费率大概在 0.7% 左右（假设支付宝和微信各占一半）。
>
> **唯一的问题还是自动续费做不了。** 每个月/每年到期时，你需要在后端跑一个定时任务（Vercel Cron 或者直接用 Supabase 的 pg_cron），查哪些用户快到期了，给他们发邮件或站内通知，让他们回来再付一次。这个体验不如 Stripe 那种自动扣信用卡丝滑，但在中国个人开发者的现实约束下，这就是最优解了。
>
