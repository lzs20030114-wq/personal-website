> ## 现有工具分析
>
> ### 一、浏览器插件类（最接近你的需求）
>
> **1. 沙拉查词（Saladict）**
> 一款专业划词翻译浏览器扩展，支持中英日韩法德西语多种权威词典，支持生词本、查词历史记录，并自带 PDF 阅读器。还支持自动 Anki 制卡和 WebDAV 同步。
>
> 不足：只能在浏览器内使用，PDF 体验依赖浏览器自带的 pdf.js，PDF 本身没有语义，只负责保持样式一致，划词显示可能不正确。阅读体验不够原生流畅。
>
> **2. 划词翻译（hcfy.ai）**
> 内置 PDF 阅读器，支持划词、悬浮取词、截图翻译，支持历史记录和收藏夹，收藏夹内容可以导出成 JSON 和 CSV。
>
> 不足：同样是浏览器插件，不是独立应用。导出的是翻译记录而非结构化的"生词表"（缺少音标、词性、例句等字段的结构化整理）。
>
> ### 二、桌面 PDF 阅读器类
>
> **3. Microsoft Edge 内置 PDF 词典**
> 选中单词后弹出 mini menu，点击 Define 即可看到释义和发音。
>
> 不足：没有生词收藏和导出功能，纯粹是即时查词，查完就没了。
>
> **4. GitHub 开源项目 PdfViewer（omeryanar）**
> Windows 端 PDF 阅读器，选中单词后自动在词典中查询并作为批注添加到文档。
>
> 不足：仅 Windows，没有生词本和导出，体验偏极客向。
>
> **5. pdfTranslator（GitHub 开源）**
> 一个具有划词翻译功能的跨平台 PDF 阅读器，面向科研人员。
>
> 不足：主要面向整句翻译，不是单词学习场景，没有生词管理功能。
>
> ### 三、电子书阅读器类
>
> **6. Kindle Vocabulary Builder**
> 阅读时长按单词自动弹出释义，所有查过的词会自动存入 Vocabulary Builder，包含释义和上下文。可以通过第三方工具（Fluentcards、KindleVocabToAnki）导出到 Anki。
>
> 不足：只支持 Kindle 格式电子书，不支持 PDF。Vocabulary Builder 功能仅限 Kindle 电子阅读器硬件，在手机 App 上不可用。导出流程繁琐（需连接电脑提取 vocab.db 文件）。
>
> ### 四、其他辅助工具
>
> **7. VocabGenerator.com**
> 可以从 PDF 中提取难词，自动创建翻译词卡，支持导出到 Anki、Quizlet、CSV 等格式。
>
> 不足：这是批量提取工具，不是阅读过程中的即时交互。你没法一边读一边标记，而是上传整个文件后一次性处理。

> ## 技术难点分析
>
> ### 1. PDF 渲染与文本提取——这是最大的硬骨头
>
> PDF 这个格式本身就是为"打印"设计的，不是为"阅读"设计的。它存储的不是"段落"和"单词"，而是"在坐标 (x, y) 处画一个字符"。这带来几个具体的技术挑战：
>
> **文本层与视觉层的对齐问题。** 用 pdf.js（Mozilla 的开源库）渲染 PDF 时，它会生成两层：一个 canvas 画布（你看到的页面）和一个透明的文本层（用于选中和复制）。这两层的位置需要精确对齐，否则你划选的文字和实际看到的文字会"错位"。不同 PDF 的字体、编码方式差异巨大，尤其是中文 PDF 或扫描版 PDF，经常出现文本层和视觉层对不齐的情况。
>
> **断词问题。** PDF 里的"单词"不一定是连续存储的。有时候一个单词的字母分属不同的文本块（text item），比如一个单词跨了两行或者用了不同的字体样式。你在双击选中一个单词时，需要靠 pdf.js 的文本层来判断词边界，但它的判断并不总是准确。换行处的连字符断词（比如 "environ-\nment"）更是一个经典难题——用户想查的是 "environment"，但选中的只是 "ment"。
>
> **扫描版 PDF 完全不可用。** 如果 PDF 是扫描件（图片型），pdf.js 提取不到任何文本。这种情况需要 OCR，而 OCR（比如 Tesseract.js）的准确率、速度和体积都是额外的挑战。作为 V1 版本，建议先只支持文本型 PDF，把这个问题标记为未来迭代。
>
> ### 2. 划词交互设计——看似简单，细节很多
>
> 你需要监听用户在 PDF 文本层上的选中事件（`selectionchange` 或 `mouseup`），然后获取选中的文本。这里有几个坑：
>
> **选中的到底是什么？** 用户可能双击选了一个词，也可能拖选了半个词、一个短语、甚至一整段。你需要做"词边界标准化"——如果用户选中的文本包含空格或标点，你需要智能判断他想查哪个词。比如用户选中了 " perspective, "（前后有空格和逗号），你需要清洗出 "perspective"。
>
> **弹窗定位。** 释义弹窗需要出现在选中单词附近，但不能遮挡正文。PDF 页面可能被缩放、滚动，弹窗的坐标计算需要考虑这些因素。同时弹窗需要在用户点击其他地方时消失，点击弹窗内的"添加到生词本"按钮时不能消失——这个事件冒泡和焦点管理需要仔细处理。
>
> **多页场景。** PDF 通常有很多页，pdf.js 出于性能考虑会做懒加载（只渲染可视区域附近的页面）。用户在不同页上划词，你需要确保文本层在当前页是激活状态。
>
> ### 3. 词典数据与查询——免费且好用的方案有限
>
> 你需要一个能根据英文单词返回释义的数据源。几个选项：
>
> **Free Dictionary API（dictionaryapi.dev）。** 免费、无需 API key，返回音标、词性、释义、例句、发音音频链接。缺点是英英释义，没有中文翻译，且词库不算全，一些低频学术词可能查不到。
>
> **有道/百度翻译 API。** 有中文释义，但需要注册开发者账号、有调用频次限制，免费额度有限。接入复杂度中等。
>
> **离线词典方案。** 可以用 ECDICT（一个开源的英中词典数据库，CSV 格式，约 77 万词条）直接打包进前端或做成本地数据库。好处是零延迟、无网络依赖、中文释义齐全。坏处是数据文件比较大（约 30-40MB），需要做索引优化。对于你"导入 PDF 就能用"的定位，离线方案其实更合理。
>
> **混合方案（推荐）。** 先查本地词典（ECDICT），查不到再 fallback 到在线 API。这样兼顾速度和覆盖率。
>
> ### 4. 生词本与导出——技术上最简单但设计上需要想清楚
>
> **数据结构设计。** 每条生词记录应该包含什么？至少要有：单词原形（lemma）、音标、词性、释义、用户查词时的上下文句子（从 PDF 中自动提取选中词所在的那句话）、来源 PDF 文件名、查询时间。上下文句子这个功能是 Kindle Vocabulary Builder 最受欢迎的特性之一，你一定要做。
>
> **词形还原（Lemmatization）。** 用户可能选中的是 "running"、"ran"、"communities"，但生词本里应该记录的是 "run"、"community"。这需要一个词形还原库（比如 JavaScript 的 `wink-lemmatizer` 或 `compromise`）。如果不做这个处理，生词本里会出现同一个词的多种形态，体验很差。
>
> **去重。** 同一个词在不同地方查了多次，生词本里应该只保留一条，但可以累计出现次数和多个上下文。
>
> **存储。** 浏览器端用 IndexedDB（比 localStorage 容量大得多，支持结构化查询）。这是个本地项目，不需要后端服务器。
>
> **导出格式。** CSV 是最通用的（可以用 Excel 打开）；Anki 导入格式（制表符分隔的 txt）对语言学习者很实用；JSON 方便程序间交互。建议至少支持 CSV 和 Anki 格式。
>
> ### 5. 性能问题
>
> **大文件 PDF。** 学术论文通常几十页还好，但如果用户导入一本几百页的教材 PDF（几十 MB），pdf.js 的加载和渲染会很慢。需要做分页懒加载，只渲染当前可视区域 ± 缓冲区的页面。
>
> **词典查询延迟。** 如果用在线 API，网络延迟会让划词后要等 200-500ms 才弹出释义，体验很差。这也是为什么推荐离线词典的原因。如果用 ECDICT 这样的大数据集，需要在 Web Worker 中加载和查询，避免阻塞主线程。
>
> ### 6. 技术栈选择建议
>
> 考虑到你是刚开始学代码，建议分两条路径思考：
>
> **Web 应用路径（推荐起步）：** React + pdf.js + IndexedDB + ECDICT。可以部署为静态网站，用户打开网页就能用，不需要安装。技术生态成熟，学习资源丰富，遇到问题容易搜到答案。
>
> **桌面应用路径（进阶）：** Electron 或 Tauri 打包成桌面应用。好处是可以更好地处理本地文件、离线使用。坏处是打包体积大（Electron 至少 100MB+），开发调试复杂度更高。建议先做 Web 版跑通，再考虑包装成桌面应用。
>

>

> ## 阅读增强
>
> **难度评估。** 导入 PDF 后自动分析全文词汇难度，给出一个类似 CEFR（A1-C2）或 Lexile 的等级评分，让用户知道这篇材料对自己来说有多难。还可以统计"你可能不认识的词大约有 X 个"，给用户一个心理预期。

> **生词密度热力图。** 在页面缩略图或滚动条旁边标注每页的生词密度——哪些页比较难、哪些页比较轻松，一目了然。用户可以选择先读容易的部分建立信心。

>
> **句子难度标注。** 不只是单词层面，还可以对长难句做标注。遇到超长的从句嵌套，自动做句法简化或者拆分显示。

> ## 词典与释义增强
>

> ## 生词本增强
>
> **艾宾浩斯复习提醒。** 生词不是记一次就完了。根据遗忘曲线，在第 1、3、7、14、30 天推送复习提醒。可以做成一个简单的内置闪卡复习模块。
>
> **生词分组与标签。** 按来源 PDF 自动分组，也支持手动打标签（比如"设计专业词汇""日常口语""GRE 词汇"）。为将来申请研究生准备学术词汇时特别有用。
>
> **掌握度追踪。** 每个词有状态：新词 → 学习中 → 已掌握。在 PDF 里再次遇到已掌握的词时，不再弹窗打扰；遇到"学习中"的词时，用不同颜色的高亮提示。
>
> **Anki 一键同步。** 不只是导出文件再手动导入 Anki，而是通过 AnkiConnect 插件直接把生词推送到 Anki 里，连模板都设计好（正面是单词+上下文句子，背面是释义+音标+词根分析）。
>
> **生词本社交。** 导出生词本时生成一个好看的分享卡片或链接，语言学校的同学之间可以互相分享——"这篇论文我查了这些词，你看看你认识几个"。
>

> ## AI 加持功能
>
> **段落/句子即时解析。** 选中一段话，不是查单词而是让 AI 解释这段话在说什么、语法结构是怎样的。对于学术论文里的长难句特别有价值。

> **AI 造句练习。** 查完一个生词后，AI 用这个词造一个贴近用户专业（比如环境艺术/设计）的例句，甚至让用户自己尝试造句然后给反馈。

> **全文摘要。** 导入 PDF 后一键生成中文摘要，帮用户在精读之前先了解大意，降低阅读焦虑。
>
> **相关词汇预学。** 在用户开始阅读之前，AI 扫描全文，提取出核心术语列表（比如 15-20 个关键词），用户可以先预习这些词再开始读，阅读效率会高很多。

> ## 为什么"全部代劳"容易翻车
>
> **pdf.js 集成是重灾区。** pdf.js 的 API 版本变动频繁，文档分散，旧代码助手 生成的代码很可能引用了过时的 API 或者错误的初始化方式。文本层对齐、Worker 配置这些细节，AI 生成的代码经常在看起来对的基础上差那么一两行配置，结果就是白屏或者文本层偏移，而你如果完全不懂代码就很难定位问题。
>
> **前端交互的"最后一公里"问题。** 划词弹窗的定位、事件冒泡、滚动时的坐标计算、多页懒加载——这些东西单独拿出来 旧代码助手 都能写对，但组合在一起时互相干扰的 bug 非常多。AI 没法看到你屏幕上弹窗飘到了奇怪的位置，你需要自己能描述问题并反复调试。
>
> **状态管理的复杂度。** 当 PDF 渲染、词典查询、生词本存储、UI 弹窗这些模块耦合在一起，整个应用的状态会变得复杂。旧代码助手 倾向于在一次生成中把所有东西塞进一个大文件，后续修改时牵一发动全身。
>
> ## 实际可行的策略
>
> 与其让 AI 一次写完，不如这样用：
>
> **逐模块推进。** 每次只让 旧代码助手 做一个小功能——先渲染 PDF、再加划词、再加查词、再加生词本。每一步都跑通了再进入下一步。这样每次出问题你知道是哪个环节的锅。
>
> **让它解释而不只是生成。** 你刚开始学代码，最有价值的不是拿到一堆你看不懂的成品代码，而是通过这个项目真正理解 HTML/CSS/JavaScript/React 的基础。让 旧代码助手 写完一段代码后，追问"这段代码每一行在做什么"。
>
> **你负责设计和验收，它负责实现。** 你画好交互原型（哪里放什么、点击后发生什么），然后让 AI 去写代码。你来判断效果对不对、体验好不好。这个分工最高效，也最能发挥你的设计优势。
>
> ## 对你来说更现实的路径
>
> 先花一到两周学基础——HTML、CSS、JavaScript 的核心概念，React 的组件和状态。不需要学很深，能看懂 旧代码助手 生成的代码、能改几行、能读懂报错信息就够了。推荐 freeCodeCamp 或 MDN 的教程，免费且系统。
>
> 然后开始用 旧代码助手 逐模块搭建项目，过程中遇到什么不懂的就问。这样你大概一到两个月能做出一个可用的 MVP，同时也真正学会了前端开发的基础。相比之下，如果直接让 AI 全写，你可能三天就拿到一个"看起来能跑"的东西，但第一个 bug 出现时你就卡死了。
>
> 要不要我先帮你规划一个分模块的开发路线图，把每一步要做什么、每一步让 旧代码助手 做什么都列清楚？
