> ## 根因
>
> [app/api/ai/route.js:418](app/api/ai/route.js:418) 只解构了 `data`，**把 `error` 扔了**：
>
> ```js
> const { data: user } = await supabaseAdmin.from("users").select(...).maybeSingle();
> if (!user) return fail(..., 403, { error: "Invalid user." });   // ← 查库失败被当成「用户不存在」
> ```
>
> Supabase REST 偶发 504（近 24 小时全项目 8 次，`/rest/v1/users` 命中 1 次）时 `data === null`，代码把**基础设施抖动误判成鉴权失败**，回 403。
>
> 前端那一层再放大一次：4 个 AI 解释 hook 的 catch 全是 `error: e.message`，而 [lib/ai/client.js:57](lib/ai/client.js:57) 造的 message 就是字符串 `"API error 403"`——所以用户眼里就是「红字 API error 403，然后没了」。按钮其实还能再点，重试基本会成功，但文案没给任何暗示。
>
> **「有时候」= 504 的发生率**，不是你账号有问题。
>
> ## 影响面

> ## 改了什么
>
> **A · 根因** — 新增 [lib/userLookup.js](lib/userLookup.js)：`lookupUserTier()` 把「查库失败」和「查无此人」彻底分开，并先自己重试一次（504 是瞬时的，重试基本就过）。
>
> [app/api/ai/route.js:419](app/api/ai/route.js:419) 接上后：
>
> | 情况 | 改前 | 改后 |
> |---|---|---|
> | DB 抖一下 | **403 Invalid user.** | 重试吸收 → 正常出结果 |
> | DB 持续失败 | 403（重试也不会好） | **503 + `[已隐去account_id]`**，台账记 `[已隐去account_id]` |
> | 码真的不存在 | 403 | 403（不变） |
>
> **B · 文案** — [lib/ai/client.js](lib/ai/client.js) 新增 `mapAiHelperError()`，4 个 explain hook（阅读/CTW/错题/造句）不再把 `e.message` 原样甩出来。浏览器里挂真组件实测：
>
> - 503 → 「服务暂时不可用，请重试」

> **回归测试** — 新增 [__tests__/user-lookup-transient.regression.test.js](__tests__/user-lookup-transient.regression.test.js)，11 条：重试吸收、持续失败回 503、真 404 用户仍 403、webhook 抛 503 且不写 processed 标记、以及「`mapAiHelperError` 对任何状态码都不得吐出 `API error`」。
