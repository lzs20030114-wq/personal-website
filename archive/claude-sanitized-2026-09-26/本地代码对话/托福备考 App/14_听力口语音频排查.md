# 托福备考 App｜听力口语音频排查

### 用户

> 我们排查到听力和口语音频并非全局资源故障：
>
> * 六类线上音频样本均正常返回 `206 Partial Content`、`audio/mpeg` 和正确的 Range。
> * 听力及口语题库共 1336 条 `audio_url`，没有空 URL。
> * `/api/audio` 同源代理、CSP和音频格式没有发现全局故障。
> * 更可能的共同根因是自动播放调用脱离了用户手势：
>    * 听力在 React `useEffect` 中执行 `play()`。
>    * 口语分别在 `setTimeout(..., 500/600ms)` 后执行 `play()`。
>    * Chrome/Safari/微信或QQ内置浏览器可能因此返回 `NotAllowedError`。
>    * 当前代码会静默吞掉部分 rejection，所以用户只看到“没有声音”。
> 需要保持真实托福体验：不能要求考生逐段手动点击“播放音频”。
> 拟定修复方案：
>
> 1. 建立统一、持久化的考试音频播放器。
>    * 在听力/口语考试最外层永久挂载一个隐藏的 `<audio>`。
>    * 整场考试期间不卸载、不重新 `new Audio()`。
>    * 每道题只修改同一个元素的 `src`。
>    * 统一处理 `playing / ended / error / stalled / NotAllowedError`。
>    * WebKit的自动播放授权更偏向按媒体元素判断，因此复用同一元素比每题创建新元素可靠。
> 2. 利用考试本来就存在的用户操作触发播放，而不是增加逐题播放按钮。
>    * 介绍页提前给持久播放器设置第一段 `src` 并 `load()`，但不播放。
>    * 用户点击“开始听力/开始口语”时，在该点击回调内同步调用同一个 `<audio>.play()`，随后再切换考试界面。
>    * 当前材料结束、考生答题期间，提前给播放器准备下一段音频。
>    * 用户点击原有的“下一题/继续”时，在点击回调内同步调用 `play()`，随后更新题目状态。
>    * 正常流程仍然表现为自动播放，考生不需要额外点击播放按钮。
> 3. 避免以下现有模式：
>
> ```
> useEffect(() => {
>   audio.play();
> }, [question]);
> ```
>
>
> ```
> setTimeout(() => audio.play(), 500);
> ```
>
>
> ```
> const audio = new Audio(nextUrl);
> audio.play();
> ```
>
> 这些调用要么脱离用户激活，要么不断创建新的媒体元素。
>
> 4. 异常兜底。
>    * `NotAllowedError`：显示一次“浏览器阻止了音频播放，请点击继续考试”的覆盖层。它只是异常恢复，不是正常交互。
>    * 网络、文件、解码失败：显示重试状态，必要时再使用 `speechSynthesis`。
>    * 口语面试不能在没播放题目的情况下静默进入录音阶段。
>    * 删除 `.catch(() => {})`，不能继续隐藏错误。
>    * 模考继续禁止任意重播，保持真实托福规则。
> 5. 增加可观测性。
> 记录模块、题型、题目 ID、音频路径、UA、`play()` 错误名称、`MediaError.code`、`readyState`、`networkState`、首帧耗时及是否走了兜底。以后收到“播不了”可以直接区分自动播放被拦、网络超时和解码失败。
> 6. 测试要求。
>    * 新访客、无媒体参与度的 Chrome。
>    * Safari及至少一次 iPhone真机验证。
>    * 微信/QQ内置浏览器真机验证。
>    * 点击“开始考试”后必须收到 `playing`，并确认 `currentTime > 0`。
>    * 点击“下一题”后，同一个 `<audio>` 更换 `src` 并成功播放。
>    * 模拟 `NotAllowedError` 时必须显示异常兜底入口。
>    * 六类真实音频各做一个线上冒烟测试。
> 希望重点评审：
>
> * “复用一个持久 `<audio>` + 利用开始/下一题点击同步播放”的方案在 Chrome、Safari及WebView是否可靠；
> * React架构下播放器应放在 ExamShell、Context Provider还是独立 controller；
> * 切换 `src`、预加载下一段与保持用户激活之间是否还有浏览器兼容陷阱；
> * 是否有比该方案更符合真实托福流程且跨浏览器更稳的实现。

> ## 四个评审点逐一回答
>
> ### 1. 持久元素 + 手势同步 play()，跨浏览器可靠吗？——可靠，且各浏览器受益机制不同
>
> - **Chrome（桌面/Android）**：sticky activation——用户在页面上有过任意一次真实点击后，整页解锁 unmuted autoplay，之后任何时机的 play() 都放行。持久元素在 Chrome 非必需但无害。
> - **Safari / iOS WebKit（含微信 iOS = WKWebView）**：按**元素**解锁。同一元素只要在手势栈内 play() 过一次，之后换 src 再程序化 play() 都被允许。这是方案的核心收益，成立——也是为什么现在每题 `new Audio()`（[RepeatTask.js:202](components/speaking/RepeatTask.js:202)、[InterviewTask.js:183](components/speaking/InterviewTask.js:183)）在 iOS 上必挂：每个新元素都没解锁过。
> - **微信/QQ Android（XWeb/X5）**：手势后播放基本放行；可加监听 `WeixinJSBridgeReady` 作为额外解锁点（老内核的经典兼容层）。
>
> **成立的硬前提**：play() 必须在 click handler 的**同步栈**里调用——在任何 `await`、`setTimeout`、setState 触发的 `useEffect` 之前。React onClick 是同步派发的，带 user activation；但 `useEffect` 在 paint 之后异步跑，已出手势栈。所以顺序必须是"onClick → controller.play(url) 同步 → 再 setState 切界面"，URL 要提前备好，不能依赖即将 setState 的数据。
>
> ### 2. 架构位置——独立 controller（纯 JS 单例）+ 薄 Context Provider，挂考试页顶层
>
> - controller 持有元素、状态机、看门狗、日志上报，**不绑 React**：因为 listening-exam、speaking-exam、mock-exam 的口语/听力模块三个壳都要用，绑进某个 ExamShell 就会被复制三份。
> - Provider 只负责把 controller 实例递给任意深度的组件，让它们能在自己的 onClick 里同步调用。挂在各考试 page 顶层即可，不要挂全局 layout（练习页不需要，也避免误用）。
> - **元素绝不能走 JSX 受控渲染**——key 变化或条件渲染会重建 DOM 节点，iOS 解锁作废。`document.createElement('audio')` 一次存进 controller，或 JSX 挂在确认永不 unmount 的层级且 src 只命令式赋值。dev 下 React StrictMode 双挂载会破坏单例，要防。
> - 现状确认：listening-exam/speaking-exam 是同页 state machine（AdaptiveExamShell），intro→考试是 state 切换不是路由跳转，所以挂 page 顶层就够，不需要跨 layout。
>
> ### 3. 切 src / 预加载 / 保持激活之间的兼容陷阱（攻击面清单）
>
> 1. **AbortError 竞态**：play() promise 还 pending 时换 src 或 pause() 会抛 "play() request was interrupted"。这是**良性**错误，统一错误处理必须白名单掉，不能弹兜底覆盖层、不能污染观测数据。切换规程：pause() → 换 src → load() → play()。
> 2. **play() 无声挂起——覆盖层触发条件要改**：iOS 上存在 play() promise 永不 settle、或 resolve 了但一直 `waiting` 不出声的案例。兜底覆盖层的触发条件不能只是"catch 到 NotAllowedError"，应该是"**play() 调用后 N 秒内没收到 `playing` 事件**"（超时兜底覆盖 NotAllowedError、静默 pending、stall 三种情况）。
> 3. **ended 单点复发**：6-26 的教训——ended 是解锁答题的唯一路径时，任何 stall 就挂死整场。新播放器要保留 timeupdate 看门狗 + 手动跳过逃生口，plan 里没提，必须写进规格。
> 4. **口语 iOS 麦克风冲突（最容易漏的真坑)**：getUserMedia 持有 mic stream 期间，iOS 把音频会话切到 play-and-record，扬声器输出会变小声甚至走听筒。持久播放器在录音阶段之后播下一题时若 stream 未释放，用户听感就是"声音没了/极小"。规格必须要求：每题录音结束立即 `stop()` 全部 tracks，下一题播放前确认 mic 已释放。真机测试必测。
> 5. **预热的局限**：答题期间给同一元素换 src + load() 预热是对的（此时元素空闲），但 iOS 低电量/低数据模式会无视 preload，load() 可能只拿 metadata——预热不保证已缓冲，播放时仍要有 buffering UI。另外确认 `/api/audio` Edge 代理的 Cache-Control 能让预热请求和正式 Range 请求命中同一缓存，否则预热是双倍流量白费。
> 6. **speechSynthesis 兜底自己也吃自动播放策略**：iOS 上首次 speak() 同样要在手势内；微信 iOS 的 speechSynthesis 基本不可用。所以 TTS 兜底要在"开始考试"手势里顺手 speak 一个空 utterance 解锁，且在微信 UA 下按"TTS 不可用"设计降级路径（显示文本/跳过），别把兜底当保底。
> 7. **后台/来电中断**：切后台、来电、Siri 会 pause 且回前台后程序化 resume 可能被拒。监听 visibilitychange，回前台若非 ended 且 paused，复用同一个"继续考试"覆盖层。
> 8. **单播放槽互斥**：现有 `activePlayerStop` 全局槽（AudioPlayer.js:226）和口语录音回放（VoiceRecorder.js:281）要和新 controller 协调，避免两个声源同时响。录音回放按钮本身是手势、用独立元素没问题，但要接入互斥。
>
> ### 4. 有没有更好的方案？——没有性价比更高的
>
> - **Web Audio API**（AudioContext resume 一次后完全自由、可无缝预载）：短句子可行，但听力讲座 3-5 分钟 mp3 解码成 PCM 要几十 MB 内存（iPhone Safari 压力大）、不可流式、iOS interrupted 状态坑更多，改造量大。不推荐为主方案。
> - **服务端按模块拼接整段长音频 + 时间戳**（真 ETS 就是连续放音）：最真实、彻底绕开逐题 play()，但要动 TTS 产线和 bank schema，是长期方向不是本次修复。
> - 结论：你的方案就是当前最优解，照单采纳 + 上面 8 条补丁。
>

> ## 对 plan 其余条目的具体修正
>
> - **介绍页预设 src + load()**：好，但建议再加一层保险——"开始考试"点击里先同步播一段几十 ms 的**静音 wav（dataURI）**完成解锁，playing 后立即换真实第一段。这样解锁不依赖第一段音频已可播（弱网下第一段还在缓冲时点开始，play() 会因 NotSupportedError/pending 把解锁搞砸）。

### 用户

> 那在用户角度 他们是否可见修改后的变化？

### 助手

> 分两类用户看：
>
> **此前音频正常的用户（大多数，桌面 Chrome 等）——基本无感知。**流程一模一样：点"开始考试"音频自动响，点"下一题"自动播下一段，全程不需要多点任何按钮。唯一可能察觉的正向差异是切题更快——答题期间已经预热了下一段，首帧延迟变小。那段几十毫秒的静音解锁 wav 人耳听不出来。
>
> **此前受影响的用户（iOS Safari、微信/QQ 内置浏览器、新访客 Chrome）——变化非常明显，这正是修复目标：**
>
> 1. 听力/口语音频从"没有声音、界面干等"变成真的自动播放。
> 2. 口语面试不会再无声跳进录音阶段——之前 InterviewTask 被拦后直接 `advance()`，用户根本不知道有题目音频，现在必然先听到题。
> 3. iOS 口语场景下，录音结束释放麦克风后，下一题的播放音量恢复正常（之前 mic 占着音频会话时声音小/走听筒的用户会感觉"声音突然正常了"）。
>
> **新增的可见 UI 只在异常时出现，正常考试全程见不到：**
>
> - "浏览器阻止了音频播放，点击继续考试"覆盖层——只在解锁失败、切后台回来、播放静默挂起时弹一次，点一下就恢复。
> - 网络/解码失败时的缓冲和重试状态（替代现在的静默无声）。
> - 现有的手动播放/跳过逃生口保留不动。
>
> **完全不可见的部分：**统一持久播放器、删除吞错、观测埋点——这些只改变我们收到"播不了"反馈时能不能直接定位原因，用户侧零感知。
>
> 一句话总结：正常用户感觉不到改动，出问题的用户从"哑巴考场"变成"和真实托福一样自动放音"；任何新增交互都只是异常兜底，不改变考试节奏。
>
> 要按上一轮说的范围（只动考试链路）出 spec 派 Opus 实施的话，说一声就开工。

### 用户

> 我的意思是 有没有负面的，就是出问题的用户被修复之后 他们的体验相比于正常用户会有不好的地方

### 助手

> 问得很关键。诚实回答：**修复本身不会给他们制造新的劣势——流程、题量、放音规则和正常用户完全一致；但有 4 处残余差距，其中 1 处（计时公平）必须在 spec 里主动设计掉，另外 3 处是平台固有、只能减轻。**
>
> **① 计时公平问题（唯一真正要设计决策的负面）。**兜底覆盖层弹出、或弱网缓冲转圈的那几秒，模块倒计时走不走？如果照走，被中断的用户等于被扣考试时间——这是修复方案里唯一可能"制造"出来的不公平。spec 里必须规定：材料播放阶段的缓冲/覆盖层期间冻结计时。顺带说，这和 6-26 遗留的 P1b"计时冻结"欠账是同一件事，这次应该一起收掉。
>
> **② 弱网/iOS 切题可能多见缓冲等待。**预热在 iOS 低数据模式下可能被系统无视，所以同样点"下一题"，桌面 Chrome 用户秒播，弱网手机用户可能先看到 1-2 秒缓冲状态。这不是修复引入的（现在他们是直接没声音），但修复后他们的体验上限仍然比桌面低一档。只能靠预热 + 缓冲 UI 减轻，消不掉。
>
> **③ 中断后要多点一次。**来电、切后台、锁屏回来后需要点一下"继续考试"才恢复放音。这类中断在手机和微信里发生率远高于桌面，所以受影响人群看到覆盖层的频率天然更高。但这是浏览器强制的，任何方案都绕不开——真实托福机考也不允许你接电话。
>
> **④ 音频彻底失败时的兜底差一档。**文件损坏或网络挂掉时，桌面用户有 speechSynthesis 机器音兜底，微信 iOS 的 speechSynthesis 基本不可用，只能降级到显示文本或跳过。发生概率很低（六类音频线上都验证过 206 正常），但一旦发生，微信用户的降级体验最差。
>
> 另外有一条**影响所有用户、不分修复前后**的：口语考试戴蓝牙耳机时，麦克风开关会让 iOS 在高音质播放模式和通话模式之间切换，可能出现 1-2 秒声音中断和音质下降。这是蓝牙协议固有的，值得在口语考试介绍页加一句"建议使用有线耳机或外放"，成本一句文案。
>
> 总结：受影响用户修复后拿到的是和正常用户**相同的考试流程**，差距只剩平台层面的网络和中断韧性；唯一需要拍板写进 spec 的是①——缓冲/覆盖层期间冻结计时，不让技术故障吃掉考生的答题时间。
